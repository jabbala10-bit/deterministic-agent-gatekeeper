# ADR-011: Evaluate against recorded trajectories, and publish where it over-blocks

**Status:** Accepted · **Date:** 2026-09-23 · **Decider:** Gunasekar Jabbala (architect/owner)

## Context
A gate is easy to make look good. Refuse everything and no attack succeeds. The only useful
evaluation reports both sides of the trade, and does it against a benchmark the author did not
design. AgentDojo is that benchmark, but running it end to end needs a model in the loop, which adds
API cost, non-determinism, and a confound: a task can fail because the agent was bad rather than
because the gate refused.

## Options considered
| Option | For | Against |
|---|---|---|
| Full AgentDojo runs with a model | End-to-end task success, the benchmark's own metric | Non-deterministic and paid; model failures and gate refusals are hard to separate; results cannot be reproduced from this repository alone |
| Hand-written attack cases | Cheap, targeted | The author writes both the attacks and the defence, which is not evidence |
| **Replay AgentDojo's ground-truth trajectories through the gate** | Deterministic, free, reproducible from this repository; the trajectories are the benchmark's, not mine | Measures decisions rather than end-to-end success; an agent reaching the same goal another way is not modelled |

## Decision
Replay the suite's recorded trajectories. For every user task, AgentDojo ships the calls a correct
agent makes; for every injection task, the calls the attacker wants. Each pair runs the user's own
trajectory up to the first call that ingests content, then the attacker's calls in that same
session, because an injection only reaches the agent through a tool result.

The human is modelled explicitly: they approve the user's own work and refuse the injection's. Both
directions are counted, because every approval is someone's attention and that cost belongs in the
results next to the security benefit.

Two policy variants are evaluated rather than one, so the trade-off is measured instead of asserted:
a **strict** variant that forbids sensitive actions once a session has ingested untrusted content,
and an **approval** variant that escalates them to a human.

`evals/RESULTS.md` is generated by the harness, and CI fails if it drifts from what the harness
produces. The caveats are part of the generated file, not a footnote someone can drop.

## Consequences
- The headline finding is the one a vendor would bury: on this suite the strict variant refuses 12 of
  16 legitimate tasks and stops no attack the approval variant did not already stop. Paying a bill
  means reading the bill first, and a rule that forbids payments after reading anything forbids
  paying bills. That is published in the README, not only in the results file.
- The attack column looks perfect because every injection in this suite ends in a payment to an
  unknown account or a password change, which is exactly what the policy guards. The generated
  results say so, and say what would not be caught.
- AgentDojo's `send_money` takes a float amount while the gate's contract is minor units, so the
  harness converts at the boundary and refuses anything not exact in cents. In production that
  conversion lives in the tool adapter, and it is precisely where a rounding bug would live.
- The benchmark's tool schemas drove three additions to the manifest language: zero-argument tools,
  boolean arguments, and fixed resource ids. Contact with someone else's tools is what found them.

## Confidence and validation
High as a measurement of what the gate decides; deliberately limited as a claim about agent safety.
The validating step is a full model-in-the-loop AgentDojo run once an API budget exists, comparing
end-to-end utility under attack with the decision-level numbers here.
